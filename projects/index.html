China Post Tracker

Track a parcel or find out what its latest status means.

Open China Post Tracker
Supported services

Look up a shipment

China Post Tracker is a web tool for checking parcels shipped through China Post, EMS, and ePacket. Enter the tracking number supplied by the seller or sender to see the latest available shipping updates. The lookup starts directly on the homepage and requires no registration, so a shopper can check an unfamiliar shipment without creating another account. If the number comes from an order confirmation, copy it as shown and keep the original confirmation handy in case you need to verify it with the seller.

Read the tracking history

International deliveries can involve several facilities, customs processing, and a handoff to a local carrier. A tracking history helps put those steps in order. Start with the latest recorded event, then look at the events immediately before it to see whether the shipment is still moving through an export facility, awaiting an update in the destination country, or approaching final delivery. The site's guide to status meanings helps readers interpret unfamiliar scan messages. The recorded events describe what the carrier has reported so far, which may be different from where the parcel is at the moment you look it up.

Troubleshoot a stalled update

The site includes guides to tracking numbers, delivery times, customs, and the final stage of delivery. These are useful when a label has been created but the carrier has yet to publish an acceptance scan, when a parcel has gone several days without a new event, or when a delivered status appears before the recipient finds the package. Start by checking the number and the date of the last scan. Depending on the situation, the next step may be to ask the seller for the carrier name, check the destination postal service, or request delivery details.

Why the lookup and guides belong together

A tracking number gives a shopper a way to find a parcel record, but the status alone can leave practical questions unanswered. Keeping the lookup and reference material on the same site supports both quick checks and more involved investigations. A shopper who only wants the latest event can start with the search box. Someone trying to understand a delay can move from the result to a guide on missing scans, customs, or last-mile delivery.

Projects in Progress

Parcel Events API

Multi-carrier tracking and webhooks

A parcel tracking API for developers who need to show shipment progress without building a separate integration for each carrier. The API is designed to accept a tracking number, return a chronological event feed, and expose a small set of consistent statuses across carriers. Responses would include the original carrier message alongside the normalized status, giving a customer support team enough context to explain an unusual scan without guessing what it means.

The design keeps the time reported by the carrier separate from the time an event was received. That distinction matters when a scan arrives late, a parcel crosses time zones, or a shipment changes hands between carriers. Carrier adapters would map location, timestamp, and event details into a shared schema. If the data is ambiguous, the response would say so and retain the carrier event rather than assigning a more precise status than the evidence supports.

The first milestone is a documented lookup endpoint, sample payloads, and a small set of adapters tested against representative tracking histories. Later work would add signed webhook delivery, retry rules, and an option to replay missed events. A sandbox would let merchants test split shipments, duplicate scans, and handoffs without waiting for real parcels. The target is a tracking feed that merchants can explain to customers and developers can debug when upstream data changes.

Delivery Desk

Shipment exceptions for merchant support

Delivery Desk is an exception queue designed for small online stores that currently look up delayed shipments one at a time. The proposed dashboard groups orders that may need attention by the reason they appeared, such as a missed delivery estimate, a failed delivery attempt, a return to sender, or an extended gap between carrier scans. Each case would show the last confirmed event, the promised delivery window, and the evidence behind the alert.

Different routes need different thresholds. A domestic parcel that misses an expected scan may be worth checking quickly, while an international shipment in customs can legitimately go longer without an update. The first version would let merchants define basic policies by carrier and shipment type and temporarily snooze a case until a chosen review date. A shared activity log would let another support agent see who contacted the carrier, what they learned, and when the customer should hear back.

The prototype would start with imported orders and tracking events. The main tests would cover split orders, tracking numbers corrected after dispatch, and parcels whose status changes after a case was closed. Later work would add optional customer update templates and reports on recurring exceptions by route. The goal is to help teams decide which shipment to investigate first and keep the next action visible until the case is resolved.

Checkout Cost Compare

Price, shipping, and import cost comparison

Checkout Cost Compare is a shopping research tool for comparing what a purchase will cost by the time it reaches the buyer. A low product price can be offset by shipping, a minimum order threshold, or charges collected later. The proposed interface would line up the item price, shipping charge, applicable discount, and any taxes or import costs the seller has disclosed. Each total would show which inputs were confirmed and which still depend on the destination or final checkout.

The comparison would be built around a specific product variant and quantity. A shopper could record size, color, package count, and seller terms before comparing offers. Delivery estimates and return windows would appear next to the price so a buyer can decide whether a cheaper offer is worth a longer wait or a more restrictive return policy. Each saved quote would include the time it was recorded, which helps when revisiting prices after a promotion ends.

The first milestone is a manual comparison workspace that lets users enter offers and return to them later. That provides a useful way to test the comparison rules before relying on automated imports. Later work would focus on recognizing common listing formats, handling currency conversion with a visible rate date, and identifying expired quotes. Tests would cover discounts that only apply above a threshold and variants with different shipping fees.

Return Route

Returns from request to refund

Return Route is a proposed returns workspace for online stores that need to follow a request from the first customer message through warehouse review and refund. It would give shoppers a clear view of the next step, including whether they need to mail an item, wait for inspection, or confirm an exchange. For merchants, the same case record would organize order lines, return reasons, label information, parcel events, and notes from warehouse and support staff.

The workflow would support partial returns, separate parcels for one order, and different outcomes for items in the same package. An item could be approved for a refund while another is still being inspected. Carrier delivery and warehouse receipt would be recorded separately, helping teams identify whether a parcel is pending intake or has already been checked. Operators would see why a case is blocked and which team can move it forward.

The first milestone would cover return requests, label details, receipt confirmation, and a review step before a refund is recorded. The project would test missing labels, parcels delivered to the wrong intake location, and late carrier events. A later version could summarize which products are frequently returned for the same reason, helping merchants decide whether to improve a product description, update sizing guidance, or look more closely at a recurring quality issue.

Storefront Stock Watch

Inventory across storefronts

Storefront Stock Watch is a proposed monitoring tool for merchants who sell the same inventory through several storefronts and marketplaces. A product can appear available on one channel after another channel has sold the last unit. The tool would give operators a single view of recently reported stock by SKU and show which sources are newer or older. Merchants could set a low stock threshold and see where a discrepancy is large enough to investigate.

The design would keep a stable internal product identity while mapping channel listings and variant identifiers to it. It would account for cases where marketplaces refer to the same color or size using different names. Bundles would have a separate rule that checks the components needed to fulfill each unit. Inventory feeds would show their last successful update time so an operator can distinguish a legitimate zero balance from a delayed or failed import.

The first release would be an observation tool with a review queue and an export of mismatched records. Merchants could validate mapping decisions and stock rules before giving an integration permission to update any channel. Later work could add automated stock reconciliation, with a preview of the proposed changes and an audit trail of what was applied. Test cases would include discontinued variants, reserved units, and changes that arrive out of order.

Post-Purchase Inbox

Order updates and return reminders

Post-Purchase Inbox is a proposed personal dashboard for shoppers who want a single place to find confirmations, tracking updates, and return deadlines. Purchases from several stores often arrive as a mix of emails, account notifications, and carrier links. The dashboard would turn those fragments into an order timeline that connects the seller, the items purchased, and the parcels carrying them. Shoppers could check what still needs action and keep useful records after delivery.

The design would start with manually added orders and optional forwarding of individual confirmation messages. It would ask the shopper to review information extracted from a forwarded message before saving it, especially when a confirmation includes several items or addresses. The data model would allow one order to have multiple shipments and would show which items still lack tracking information. Return reminders would use dates confirmed by the shopper or clearly stated in the saved material.

The first milestone would cover an order list, parcel status history, and reminders for approaching return deadlines. Users could export or delete their saved records. Later work would explore aligning messages from the same order, recognizing shipment splits, and reducing duplicate alerts when several services report the same event. The project would test whether people can reliably answer three questions from the dashboard: what has arrived, what is still in transit, and which decisions need to be made soon.

Fulfillment Pulse

Shipping and fulfillment analytics

Fulfillment Pulse is a proposed analytics workspace for e-commerce teams that want to understand how long orders spend at each stage after checkout. A single delivery average can hide differences between warehouses, shipping methods, and destinations. The dashboard would break the timeline into order processing, time to first carrier scan, transit time, and final delivery. Teams could compare those measures over time and open the underlying shipment records when a change needs investigation.

The project would define which timestamps count toward each measure and show how many shipments have enough information to be included. For example, a shipping label timestamp and a carrier acceptance scan answer different questions. Orders with missing scans would appear in a coverage summary rather than silently distorting the results. The workspace would also keep the delivery promise recorded at checkout, giving teams a consistent basis for measuring whether a shipment arrived on time.

The first milestone is a weekly report built from order exports and shipment histories. It would include a breakdown by fulfillment location and shipping method and a list of records that could not be matched. Later work could add scheduled ingestion and alerts when transit time or scan coverage shifts materially. The intended workflow is to start with a measurable change, open several representative orders, and decide whether the next step belongs with the warehouse, the carrier, or the storefront team.
